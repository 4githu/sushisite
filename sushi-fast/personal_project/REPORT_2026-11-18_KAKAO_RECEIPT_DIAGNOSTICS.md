# 카카오 이미지 발신 확인 조사 (2026-11-18)

## 확인된 사실
- 사용자 보고: 이미지가 실제 도착했으나 뒤따르는 텍스트는 진행되지 않았다.
- 오류 확인 번호 `977a03cdb308462289fafe69c413cc37`은 이미지 발신 클릭 후 새 발신 이미지 행을 확인하지 못한 `delivery_not_observed`, `uncertain=True`. 도우미 소요 27.749초. 사용자 확인과 모순되지 않는다.
- 코드상 이미지 확인 실패가 후속 텍스트를 중단한다. 같은 시각 DB에 이미지 unknown, 텍스트 not_started 기록이 있으나 브리지 ID와 DB ID는 직접 연결되지 않아 동일 요청이라고 확정하지 않는다.
- 당시 행 정보와 세부 판정 기록이 없어 정확히 어떤 조건이 실패했는지 확정 불가. 기존 미확인 요청 재발송 없음.

## 변경
- 새 발신 이미지 행의 방향, 이미지 분류, 이미지/시계/공유/텍스트 요소 존재, 이전/이후/새 행 수, AX 시간 예산 초과 여부를 집계해 실패 진단에 기록한다. 본문, 행 식별자 및 AX 레이블은 기록하지 않는다. 확인 성공 조건과 재전송 정책은 변경하지 않았다.
- 고정 합성 점검 도구에 `--keep-room-open` 옵션을 추가하여 이미지 다음 텍스트 경로를 점검할 수 있다.
- 합성 진단 검사는 방향 불명 등 판정 조건과 개인내용 제외를 검증한다. 유관 카카오 테스트 125개 통과. Swift 후보 빌드 성공. 활성 작업 부재 확인 및 UI 락 후 도우미 교체와 백엔드 재시작; OpenAPI 200.

## 실제 본계정 합성 점검
- 반영 후 이미지 후 창 유지, 텍스트 후 창 닫기: 도우미 발신 행 확인과 정리 상태 성공.
- 별도 시험에서 이미지 두 건 연속 후 텍스트: 세 건 모두 도우미 발신 행 확인과 정리 상태 성공. 모두 새로운 고유 시도. 확인 조건 자체가 잘못될 가능성이 있으므로 이는 독립적인 수신 증명이 아니며, 학생 방이나 실제 리포트 동일 경로의 해결 증거가 아니다.

## 한계
- 원 사건을 재현하지 못했고 근본 원인과 제품 결함 해결은 미확정이다. 다른 새 이미지가 성공으로 분류될 수 있는 판정 한계도 있으나, 실제 해당 사건의 원인이라는 증거는 없다. 동일 학생 방 발송은 승인 범위 밖이므로 하지 않았다. 새로운 오류에서만 추가 진단이 수집되며 과거 결측 데이터를 복구하지 않는다.

## 후속 실제 리포트 재현 및 수정
- 위 최초 조사 이후 사용자가 동일 실제 리포트의 본계정 시험을 명시적으로 허용했다. 현재 저장된 대상 리포트를 운영 코드의 PDF→이미지 경로로 4장 생성해 하나의 이미지 묶음 및 실제 후속 안내문을 `send_clinic_job`으로 시험했다. 기존 요청은 재시도하지 않았고 각 시험은 새 작업 ID다. 운영 DB의 리포트 상태는 바꾸지 않았다.
- 본계정 창을 도우미의 cleanup 명령으로 닫은 뒤 기존 운영 도우미로 실행한 시험에서 `delivery_not_observed`, 이미지 `unknown`, 텍스트 `not_started`를 재현했다. 추가 진단 후보로 한 새 시험에서 새 사진 행 1개, 이미지·공유 요소 존재, 시계 0개, 방향 unknown, AX 예산 초과 없음이 기록됐다. 창 기준 이미지 좌우 위치는 각각 302/968 퍼밀이었다.
- 관측한 직접 원인은 시계 없는 묶음 사진에서 방향 판정이 unknown에 머물러 발신 확인을 실패한 것이다. 원 사건 자체에는 당시 개별 판정 로그가 없어 이와 동일 원인이라고 단정할 수 없다.
- 시계가 없는 다중 이미지 묶음일 때 사진 분류, 프로필 부재와 엄격한 오른쪽 정렬을 함께 요구하는 후보를 구현했다. 반대 방향·프로필 존재·단일 이미지 등 합성 회귀와 관련 127개 시험 통과. 후보 및 운영 반영 후 각각 새 시험에서 4장 이미지와 텍스트 단계가 모두 도우미 판정상 verified였다. 운영 도우미 교체 및 백엔드 재시작 후 OpenAPI 200.
- 이 검증은 CLI에서 실제 앱 발송 함수를 호출해 본계정에 보낸 결과다. 사용자 화면/API에서 실행한 전체 경로와 학생 방은 검증하지 않았다. 현재 리포트를 재렌더링한 이미지이므로 당시 전송된 원본 파일과 바이트 동일하다고 입증하지 못했다. 이미지 행 확인은 AX 휴리스틱이며 요청 파일의 내용이나 개별 장수를 독립적으로 증명하지 않는다.
- 추가 조사: 당시 이미지 임시 파일은 조사 범위에서 찾지 못했다. 도우미 작업 디렉터리는 전송 종료 시 정리하는 구조이고 일부 위치는 접근하지 못했으므로 기기 전체에 원본이 없다는 뜻은 아니다. DB 기록과 브리지 작업 번호의 직접 연결도 남아 있지 않다.
- 정정: 위의 '리포트 상태는 바꾸지 않았다'는 호출 의도와 사후 draft 상태를 말한다. 시험 프로세스는 운영 DB를 사용해 브리지 모듈을 import했으며, import 시 outbox 테이블 초기화 및 `running`→`unknown` 복구 UPDATE를 실행한다. 시험 전 과정을 DB 읽기 전용으로 검증한 것은 아니다. 사후 점검에서 리포트는 draft였고 해당 재시작 복구 사유의 unknown outbox는 0건이었다. 다음 시험에는 격리 DB와 운영 UI와 동일한 파일 잠금을 사용해야 한다.
