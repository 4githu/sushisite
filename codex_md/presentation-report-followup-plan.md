## 1. 목적

현재 구현된 전체 발표 분석 리포트 기능을 안전하게 merge·배포하기 위해 남아 있는 확인 사항과 후속 작업을 정리한다.

작업은 다음 두 범주로 구분한다.

- **Merge 전 필수 작업**: 권한 검증, 프론트엔드 정적 검사 등 배포 안전성에 직접 영향을 주는 항목
- **Merge 후 고도화 작업**: 긴 발표 처리, 비동기 작업, 데이터 보존 정책 등 운영 안정성과 사용자 경험을 개선하는 항목

## 2. 현재 구현 상태

완료된 기능:

- 발표 구간별 전사, 내용·전달 평가, 음성 지표, E/V/C 상태 누적
- 전체 발표 점수 및 상세 분석 집계
- 시점별 피드백과 청중 반응 그래프 생성
- OpenAI 기반 전체 발표 인사이트와 실패 시 fallback
- 멱등성을 갖는 발표 종료 API
- 리포트 상태 조회 API
- ODI 세션 및 사전 세션 저장 경로
- 프론트엔드 리포트 타입과 API 메서드
- 백엔드 전체 테스트 86개 통과

남아 있는 주요 위험:

1. 종료 API의 사용자·템플릿·사전 세션 소유권 검증이 충분하지 않다.
2. Node/npm 부재로 프론트엔드 정적 검사를 실행하지 못했다.
3. 긴 발표 전사에 대한 컨텍스트 제한 처리가 아직 단순하다.
4. 리포트 생성 상태가 메모리에만 존재하여 프로세스 재시작에 취약하다.
5. 실제 프론트엔드 발표 종료 UX가 EVC 세션 자격 증명과 완전히 연결되지 않았다.
6. 전사와 발표 자료의 보존·삭제 정책이 정의되지 않았다.

## 4. Merge 전 필수 작업

### 4.1 종료 API 권한 및 소유권 검증

#### 문제

현재 `ReportFinishRequest`는 다음 식별자를 요청 본문에서 받을 수 있다.

- `user_id`
- `template_id`
- `pre_session_pin`
- `template`

EVC 세션 토큰만 유효하면 요청자가 전달한 대상에 리포트 저장을 시도할 수 있으므로, 다른 사용자의 템플릿이나 사전 세션에 결과가 연결될 가능성을 차단해야 한다.

#### 권장 설계

EVC 세션 생성 시 서버가 소유권을 한 번 검증하고 연결 정보를 `SessionRecord`에 고정한다.

```text
ODI 로그인 사용자
→ 소유한 pre_session 조회
→ EVC smart-start
→ 서버가 user_id/template_id/pre_session_pin을 SessionRecord에 고정
→ finish 요청은 request_id와 시간 정보만 전달
→ 서버가 SessionRecord의 고정된 연결 정보로 저장
```

종료 요청에서 `user_id`, `template_id`, `template`을 다시 받지 않는 것이 가장 안전하다.

#### 구현 작업

1. `smart-start`에 선택적인 `pre_session_pin`을 추가한다.
2. ODI 로그인 쿠키에서 사용자 ID를 읽는다.
3. `pre_session_pin`이 로그인 사용자 소유인지 확인한다.
4. 연결된 `template_id`, `user_id`를 서버가 조회한다.
5. 다음 필드를 `SessionRecord`에 저장한다.

```python
owner_user_id: str | None
template_id: str | None
pre_session_pin: str | None
```

6. `ReportFinishRequest`에서 다음 필드를 제거한다.

```text
user_id
template_id
template
pre_session_pin
```

7. `report_service._persist_report()`가 요청값이 아니라 `SessionRecord`의 연결 정보만 사용하도록 변경한다.
8. 사전 세션이 이미 완료·취소·만료되었으면 종료 요청을 거부한다.
9. 이미 다른 영구 세션이 연결된 사전 세션에는 새 세션을 만들지 않는다.
10. 리포트 저장과 `pre_session` 연결을 하나의 DB 트랜잭션으로 처리한다.

#### 대상 파일

- `sushi-fast/odi/EVC/router.py`
- `sushi-fast/odi/EVC/pipeline.py`
- `sushi-fast/odi/EVC/session_store.py`
- `sushi-fast/odi/EVC/report_schema.py`
- `sushi-fast/odi/EVC/report_service.py`
- `sushi-fast/odi/db/odidb.py`
- `sushi-fast/odi/db/router.py`

#### 테스트

- 소유한 사전 세션으로 EVC 시작 성공
- 다른 사용자의 사전 세션으로 시작 시 `403`
- 존재하지 않는 PIN은 `404`
- 만료·취소·완료된 사전 세션은 `409`
- 요청 본문으로 다른 `user_id`를 주입할 수 없는지 확인
- 동일 종료 요청이 영구 세션을 하나만 생성하는지 확인
- DB 저장 도중 실패하면 사전 세션 연결과 세션 생성이 함께 rollback되는지 확인

#### 완료 기준

- 클라이언트가 영구 저장 대상 사용자나 템플릿을 임의로 지정할 수 없다.
- EVC 세션과 ODI 세션 사이의 연결이 서버에서 검증되고 고정된다.
- 다른 사용자의 리포트 생성·조회·연결이 통합 테스트에서 모두 거부된다.

## 5. 실제 발표 종료 및 생성 상태 UI

### 5.1 문제

프론트엔드에는 EVC 종료 및 상태 조회 메서드가 추가되었지만, 실제 발표 종료 화면은 아직 EVC `session_id`와 `session_token`을 소유하고 있지 않다. 현재 일반 발표 흐름은 `pre_session` 상태 polling을 사용한다.

### 5.2 구현 방향

Unity와 웹 사이의 책임을 명확히 선택해야 한다.

#### 권장안: Unity가 종료 요청, 웹은 ODI 상태 조회

1. 웹이 사전 세션을 생성한다.
2. Unity가 PIN으로 발표 설정을 가져온다.
3. Unity가 서버에서 EVC 세션을 시작하고 토큰을 안전하게 보관한다.
4. 발표 종료 시 Unity가 마지막 오디오 처리 완료를 기다린다.
5. Unity가 EVC `finish`를 호출한다.
6. 서버가 리포트를 영구 저장하고 `pre_session.state`를 `finished`로 변경한다.
7. 웹은 기존 `pollUntilFinished()`로 완료를 감지한다.
8. 웹은 연결된 ODI `session_id`로 리포트 상세 페이지를 연다.

웹에 EVC 토큰을 전달하지 않아도 되므로 이 구조가 더 안전하다.

### 5.3 UI 상태

다음 상태를 화면에서 구분한다.

| 상태 | UI |
|---|---|
| `waiting` | PIN과 접속 대기 안내 |
| `running` | 발표 진행 중 안내 |
| `finishing` | “전체 발표를 분석하고 있어요” 진행 상태 |
| `finished` | 리포트 보기 버튼 활성화 |
| `failed` | 데이터 보존 안내와 재시도 버튼 |
| `expired/cancelled` | 세션 재생성 안내 |

현재 `pre_sessions.state`에는 `finishing`과 `failed`가 없으므로 상태 스키마를 확장하거나 별도의 `report_job_status`를 조회해야 한다.

### 5.4 테스트

- 마지막 오디오 요청 완료 후에만 종료 요청 실행
- 종료 버튼 연속 입력에도 요청 1회
- 분석 중 리포트 버튼 비활성화
- 분석 완료 후 자동으로 리포트 버튼 활성화
- 실패 후 동일 데이터로 재시도 가능
- 페이지 새로고침 후에도 생성 상태 복구

### 5.5 완료 기준

- 발표 종료부터 리포트 열기까지 수동 JSON 전달이 필요 없다.
- 고정 `fixedDemoFeedback`은 체험용 경로에서만 사용된다.
- 실제 발표 경로에서 생성 상태와 실패 사유를 확인할 수 있다.

## 6. 긴 발표 계층 요약 및 컨텍스트 제한

### 6.1 문제

현재 AI 인사이트 입력은 모든 구간 전사와 메모를 한 번에 전달한다. 발표가 길면 모델 컨텍스트 한도 초과, 비용 증가, 응답 지연이 발생할 수 있다.

### 6.2 구현 작업

1. 최대 입력 문자 수 또는 토큰 수 설정을 추가한다.

```text
EVC_REPORT_MAX_INPUT_TOKENS
EVC_REPORT_CHUNK_TOKENS
EVC_REPORT_MAX_EVIDENCE_SEGMENTS
```

2. 구간을 슬라이드 또는 시간 창 단위로 묶는다.
3. 각 묶음에서 다음 정보를 구조화해 요약한다.

- 핵심 주장
- 사용한 근거
- 발표 구조상 역할
- 강점과 개선점
- 원본 step 및 시간 범위

4. 최종 인사이트에는 다음만 전달한다.

- 슬라이드별 계층 요약
- 결정적 점수 집계
- 최상·최하 평가 구간 원문
- 주요 전환 구간
- 원본 step 참조

5. 모델이 반환한 step이 실제 원본에 존재하는지 검증한다.
6. 앞부분을 단순 삭제하는 truncation은 사용하지 않는다.

### 6.3 캐시

동일한 발표 구간 요약은 다음 키로 캐시한다.

```text
hash(model + prompt_version + normalized_segment_text)
```

리포트 재시도 시 이미 생성된 구간 요약을 재사용한다.

### 6.4 테스트

- 짧은 발표는 단일 단계로 처리
- 긴 발표는 여러 chunk로 분할
- 모든 chunk가 최종 요약에 반영
- 원본 첫·중간·마지막 구간이 누락되지 않음
- 잘못된 step 참조 거부
- 모델 컨텍스트 제한보다 입력이 작게 유지됨
- 동일 입력 재시도 시 chunk 캐시 사용

### 6.5 완료 기준

- 설정된 최대 입력 크기를 초과하지 않는다.
- 긴 발표에서도 처음과 마지막 내용이 모두 최종 분석에 반영된다.
- 최종 피드백이 실제 원본 step으로 추적 가능하다.

## 7. 영구 작업 상태 및 프로세스 재시작 복구

### 7.1 문제

현재 리포트 생성 상태와 누적 구간 데이터는 `SessionStore` 메모리에 있다. 서버 재시작 또는 TTL 만료 시 생성 작업과 원천 데이터가 사라질 수 있다.

### 7.2 데이터 모델

다음 테이블을 추가한다.

```text
presentation_report_jobs
presentation_segments
presentation_reports
```

#### `presentation_report_jobs`

- `job_id`
- `evc_session_id`
- `odi_session_id`
- `request_id`
- `status`: `not_started | queued | generating | ready | failed`
- `attempt_count`
- `error_code`
- `error_message_safe`
- `created_at`, `started_at`, `finished_at`, `updated_at`

#### `presentation_segments`

- `evc_session_id`
- `step`
- `client_time_s`
- `slide_index`
- `transcript`
- `evaluation_json`
- `speech_metrics_json`
- `evc_state_json`
- `warnings_json`

`(evc_session_id, step)`를 unique key로 사용한다.

#### `presentation_reports`

- `report_id`
- `odi_session_id`
- `version`
- `feedback_json`
- `generator`
- `generated_at`

### 7.3 구현 작업

1. 각 유효 구간 완료 시 메모리와 DB에 동일 step을 upsert한다.
2. 종료 요청 시 `request_id` unique constraint로 작업을 생성한다.
3. 생성 상태 변경을 트랜잭션으로 처리한다.
4. 서버 시작 시 `generating` 상태에서 오래 멈춘 작업을 검색한다.
5. 재시도 가능한 작업은 `queued`로 되돌린다.
6. 최대 재시도 횟수를 넘은 작업은 `failed`로 확정한다.
7. EVC 메모리 세션이 없어도 DB 구간 데이터로 리포트를 재생성할 수 있게 한다.

### 7.4 테스트

- 동일 step 재전송 시 중복 저장 없음
- 동일 request ID로 작업 하나만 생성
- 생성 도중 프로세스 중단을 모사한 복구 테스트
- 메모리 세션 삭제 후 DB 데이터로 리포트 생성
- 완료된 작업을 재호출하면 동일 결과 반환
- 실패 상태와 안전한 오류 코드 조회

### 7.5 완료 기준

- 서버 재시작 후에도 발표 데이터와 리포트 작업 상태가 유지된다.
- 동일 발표에 중복 영구 리포트가 생성되지 않는다.
- 운영자가 실패 작업의 상태와 재시도 여부를 확인할 수 있다.

## 8. 전사 및 발표 자료 보존·삭제 정책

### 8.1 분류

데이터를 다음처럼 구분한다.

| 데이터 | 민감도 | 권장 기본 보존 |
|---|---|---|
| 원본 오디오 | 높음 | STT 완료 후 즉시 삭제 또는 최대 24시간 |
| 전체 전사 | 높음 | 30일 또는 사용자 선택 |
| 슬라이드/스크립트 | 높음 | 세션 삭제 또는 설정된 만료일까지 |
| 구간 평가·점수 | 중간 | 리포트 보존 기간과 동일 |
| 최종 리포트 | 중간 | 계정 유지 기간 또는 사용자 삭제 시까지 |
| 모델 요청/응답 로그 | 높음 | 기본 저장 금지 |

실제 보존 기간은 서비스 정책과 개인정보 처리방침 검토 후 확정한다.

### 8.2 구현 작업

1. 데이터 종류별 `expires_at`을 저장한다.
2. 백그라운드 정리 작업을 구현한다.
3. 사용자 리포트 삭제 시 관련 전사·구간 평가·자료도 함께 삭제한다.
4. 파일 삭제와 DB 삭제의 실패를 추적한다.
5. 로그에는 전체 전사, 슬라이드 본문, 토큰을 남기지 않는다.
6. 사용자에게 다음 기능을 제공한다.

- 전체 전사 다운로드
- 전사만 삭제
- 리포트와 원천 데이터 전체 삭제
- 보존 기간 확인

### 8.3 테스트

- 만료된 원본 오디오 삭제
- 보존 중인 리포트는 삭제되지 않음
- 사용자 삭제 요청 시 연관 데이터 cascade 삭제
- 파일 삭제 실패 시 재시도 대상으로 기록
- 로그에 원문과 세션 토큰이 포함되지 않음

### 8.4 완료 기준

- 모든 민감 데이터에 보존 기간 또는 명시적인 영구 보존 근거가 있다.
- 사용자가 자신의 원천 발표 데이터를 삭제할 수 있다.
- 삭제 결과가 DB와 파일 저장소에서 일치한다.

## 9. 비동기 작업 큐 및 운영 관측성

### 9.1 적용 시점

MVP의 동기 생성 시간이 HTTP 제한 안에 안정적으로 들어오면 바로 도입할 필요는 없다. 다음 조건 중 하나가 발생하면 도입한다.

- 리포트 생성 p95가 10초 이상
- 동시 생성 요청으로 API 응답 지연 발생
- 다단계 요약으로 외부 모델 호출이 여러 번 필요
- 재시작 후 작업 복구가 필요

### 9.2 구현 작업

1. FastAPI 요청은 작업 생성 후 `202 Accepted`를 반환한다.
2. 워커가 `queued` 작업을 가져가 처리한다.
3. 상태 조회는 DB 작업 상태를 반환한다.
4. 재시도는 지수 backoff와 최대 횟수를 적용한다.
5. 다음 지표를 수집한다.

- 생성 성공·실패 건수
- 생성 단계별 latency
- 입력 구간 수와 단어 수
- 모델 호출 횟수와 fallback 비율
- retry 횟수
- 작업 queue 대기 시간

6. 로그에는 `job_id`, `evc_session_id`, 단계, 안전한 오류 코드만 기록한다.

### 9.3 완료 기준

- 웹 요청 타임아웃과 무관하게 생성 작업이 완료된다.
- 중복 작업이 동시에 실행되지 않는다.
- 실패 원인을 민감 데이터 노출 없이 추적할 수 있다.

## 10. 점수 기준 보정 및 비교 통계

### 10.1 현재 정책

- 종합 점수는 결정적 집계 규칙을 사용한다.
- 비교 모집단이 없으므로 percentile은 `null`이다.
- LLM은 점수나 백분위를 임의로 생성하지 않는다.

### 10.2 데이터 확보 후 작업

1. 익명화된 평가 데이터와 전문가 라벨을 수집한다.
2. 지표별 분포와 상관관계를 확인한다.
3. 현재 가중치와 전문가 평가의 오차를 측정한다.
4. 발표 목적·언어·길이별 점수 편향을 분석한다.
5. 점수 산식 버전을 리포트에 저장한다.
6. 충분한 표본과 대표성이 확보된 경우에만 percentile을 제공한다.

### 10.3 완료 기준

- 점수 산식 변경 전후를 버전으로 구분할 수 있다.
- 동일 입력과 동일 버전에서 동일 점수가 생성된다.
- percentile의 모집단, 표본 크기, 기준 기간을 설명할 수 있다.

- [ ] 프론트엔드 check/lint/unit test가 통과한다.

## 13. 최종 완료 기준

다음 조건을 모두 충족하면 전체 발표 분석 리포트 기능을 운영 준비 완료로 판단한다.

1. 인증된 사용자와 소유한 발표 세션만 리포트를 생성·조회할 수 있다.
2. 발표 종료부터 리포트 화면까지 자동 흐름이 연결된다.
3. 긴 발표와 외부 AI 실패에도 추적 가능한 리포트가 생성된다.
4. 서버 재시작과 중복 요청에도 데이터가 유실되거나 중복 생성되지 않는다.
5. 전사와 발표 자료의 보존·삭제 정책이 코드와 사용자 UI에 반영된다.
6. 백엔드·프론트엔드·Unity 통합 테스트가 CI에서 재현 가능하게 통과한다.
